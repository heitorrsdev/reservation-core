# ADR 0011 – Application-Controlled Timestamps

## Context

Historically, the database schema defined the `created_at` timestamp columns using PostgreSQL's native `DEFAULT NOW()`. This meant the database assumed the responsibility of generating timestamps at the moment of insertion if the application omitted them.

However, in a strict Domain-Driven Design (DDD) approach, the domain should own its data and invariants, not the database. Relying on default database values creates a scenario where the application layer is unaware of the exact moment an entity was created until it refetches that entity, leading to potential inconsistencies between the application's in-memory model and the persisted state. It also creates drift between how data behaves in tests versus production.

To address this, migration `0006_remove_default_now_from_created_at.sql` was introduced, stripping the `DEFAULT NOW()` constraints from the persistence layer.

## Decision

1. **`createdAt` is always generated at the application layer**
   Timestamps are no longer generated by the database. The `DEFAULT NOW()` behavior for timestamp columns has been completely removed.

2. **Entities explicitly manage their timestamps**
   - The static `create()` factory method on Domain Entities (used for instantiating new entities) internally assigns `createdAt: new Date()`. It never accepts `createdAt` as an external input parameter.
   - The static `reconstitute()` factory method (used exclusively by infrastructure mappers) accepts all fields, including `createdAt`, to rebuild business objects from the persisted database rows.

## Consequences

### Positive

* **Domain Authority**: The domain dictates the exact timestamp of creation, preserving the source of truth entirely within the application layer.
* **Consistency**: Predictable behavior across unit tests, integration tests, and production environments, as the application generates the exact same timestamp logic regardless of the environment.
* **No Hidden Persistence Behavior**: The database acts strictly as a dumb storage mechanism, removing implicit logic (like `DEFAULT NOW()`) that developers might overlook.

### Negative / Trade-offs

* **Application Responsibility**: The application must always provide the `createdAt` value; failing to do so will result in a database error rather than quietly succeeding with a default value.
* **Manual Data Entry Burden**: The database can no longer independently generate valid records with timestamps; manual insertions via SQL clients require the user to explicitly define the `created_at` value.

These trade-offs are deliberate and technically justified, fully respecting the rule that the domain must never depend on infrastructure logic or accept hidden data mutations.
